# Intermediate

Buona parte dei modelli sono stati impiegati come delle tabelle di un DB relazionale. Dalle 19 colonne di partenza ho preferito dividerlo in macro-aree che contenessero informazioni tra esse correllate.

So benissimo di aver aggiunto 'difficoltà' al codice da scrivere, alla lineage che risulta essere meno manutenibile e soprattutto se si dovesse aggiungere un nuovo campo o venisse rinominato uno precedente, a cascata si dovrebbe mettere mano a tutte le dipendenze, moltiplicando il lavoro.

Ma volevo divertirmi un poco con le Join ed utilizzare dbt in maniera un po' diversa da come sia stato concepito. Nel caso le performance fossero fondamentali al massimo, utilizzerei il modello di staging stg_trip__speed_filtered e lo salverei come tabella e non vista

# int_zone__pickup_summary
```sql
WITH
pickup_zones AS (
    SELECT
        trip_id,
        start_location_id,
    FROM {{ ref('int_trip__temporal_spatial') }}
),

revenues AS (
    SELECT
        trip_id,
        total_amount
    FROM {{ ref('int_trip__prices') }}
),

joined AS (
    SELECT 
        pickup_zones.start_location_id AS pickup_zone,
        revenues.total_amount
    FROM pickup_zones
    JOIN revenues ON pickup_zones.trip_id = revenues.trip_id
)

SELECT
    pickup_zone,
    COUNT(*) AS num_trips,
    TRY_CAST(SUM(total_amount) AS DECIMAL(10, 2)) AS total_revenue
FROM joined
GROUP BY pickup_zone
```
Unico modello 'lodevole' per sfruttare la modularità ed evitare di dover riscrivere la JOIN in 2 marts [top5_by...] che utilizzano 'int_trip__temporal_spatial' e 'int_trip__prices'
